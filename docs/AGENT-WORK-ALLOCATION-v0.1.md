# Gemina — распределение работы и независимых проверок v0.1

**Дата:** 2026-11-04. **Статус:** согласованная организационная рекомендация, runtime **NOT_RUN**. Эта схема не создаёт агентов, не назначает владельцу расходы, не даёт права на запуск или merge.

Основания: [MVP Baseline](MVP-BASELINE-v0.1.md), [M0 Passport](M0-IMPLEMENTATION-PASSPORT-v0.1.md), [уровни сложности A/B/C](proposals/2026-11-04-DIFFICULTY-AND-AGENT-MODES.md) (из PR #10), [независимое слепое сравнение](proposals/2026-11-04-INDEPENDENT-BLIND-AGENT-EVALUATION.md) (из PR #11).

## Два независимых измерения

- **A/B/C = риск тихой ошибки** и необходимая строгость проверки, а не «ранг» модели и не баллы соревнования.
- **Режим = как выполняется работа:** один исполнитель + аудит; две изолированные независимые реализации; независимые test fixtures; blind review результатов.
- **Не дублировать всё:** параллельная реализация имеет смысл только при небольшом, фиксированном контракте и достаточном бюджете; работа над первым ядром важнее чемпионата. При внешних ограничениях можно выполнить независимые fixtures вместо второго полного кода.

## Предлагаемые роли на первый цикл

| Роль | Кому предложить | Ответственность | Границы независимости |
|---|---|---|---|
| **Владелец / финальное решение** | LL1yt | Допустить запуск M1, выбрать модели и ресурсы, утвердить изменения контракта, выбор победителя и merge | Судить сначала анонимно; право не выбирать победителя |
| **Координатор / хранитель контракта** | Архивариус (ChatGPT), при доступности | Свести требования, зафиксировать SHA, следить за границами, готовить слепые пакеты и сопоставлять результаты | Не быть единственным судьёй своих собственных допущений; не приписывать себе запусков |
| **Независимый разработчик A** | Моргана (доступный OpenAI coding-агент, например Codex) | Создать собственные sampler fixtures и отдельную реализацию M1 по замороженному контракту | До фиксации результата не видеть решения B |
| **Независимый разработчик B** | Вергилий (Claude Code) | То же задание, собственные fixtures и собственная реализация M1 | До фиксации результата не видеть решения A |
| **Независимый технический судья** | Не участвовавший в разработке агент другой модели + владелец | Проверить математический контракт, тесты, качество кода и воспроизводимость; затем анонимно оценить A/B | Скрыть имена/атрибуцию до фиксации оценки; проверить общий источник ошибок |
| **Интегратор** | По итогам проверки один назначенный coding-агент | Интегрировать выбранный минимальный вариант и пройти обязательные S/G-тесты | Отдельный PR, без немедленного слияния без разрешения |

Имена — **предложения распределения, не факт назначения**. Моргана, Вергилий и Архивариус могут иметь различный доступ к GitHub, Slack, локальному Mac и SDK; проверить фактическое окружение перед работой. Не утверждать априори, что один производитель или модель сильнее. Конкретную модель/режим усилий, версии, цену и tool access записать до сравнения. Один и тот же агент может участвовать в других испытаниях в иной роли, но не оценивать собственную попытку вслепую.

## Этапы M0–M7: режим по умолчанию

| Этап | Риск | Рекомендуемая работа | Контроль / стоп-условия |
|---|---|---|---|
| **M0** | B | Архивариус/Моргана сверяет паспорт; Вергилий независимо проверяет против PR #2/#5 | Контракт/версии/входы согласованы, runtime ещё NOT_RUN |
| **M1 sampler** | B код, A fixtures | **Первый мини-конкурс** двух изолированных реализаций (Моргана и Вергилий); если это задержит MVP — одна реализация и два независимых fixture-набора | Общие S01–S05 и ручные expected values; анонимная оценка |
| **M2 gradients** | A | Один основной реализатор после M1 + независимый пакет аналитических/finite-difference тестов другого агента; опциональный второй конкурс | G01–G04, производные внутри ячейки, односторонние швы; не замалчивать fail |
| **M3 Lion + W** | A | Один реализатор, второй — независимый аудитор полного графа | Все пути включая W→r₀→GRU, full BPTT и диагностика адресов; C01–C05/O01 |
| **M4 first train** | B→A при проблемах | Один runner; другой агент аудирует split, LR, mask и update | T01–T05, честные статусы; отсутствие обучения → эскалация |
| **M5 replay** | B | Один реализатор + независимый review / round-trip тесты | R01–R05 |
| **M6 научные сравнения** | A | Один фиксированный экспериментальный протокол, независимая интерпретация одних результатов до обмена мнениями | E01–E05, несколько seeds, справедливые сравнения и INCONCLUSIVE допускается |
| **M7+** | A | Отдельное поручение после результатов ядра | Не является обязательной частью MVP |

## Минимальный старт M1 (готовить, но не выполнять автоматически)

1. Записать **immutable task card** и полный SHA M0, PR #5 Mathematical/Training/Test Matrix; проверить toolchain. Текст задания двум исполнителям дословно одинаковый, исключая маркировку кандидатов и секретные параметры подключения.
2. Оба **сначала независимо** готовят аналитические expected values, negative/wrap fixtures, проверку осей и формы [B,8,C] по спецификации (S01–S05), не читая чужие работы.
3. После отдельного разрешения реализации каждый делает собственный маленький sampler в своей изолированной области. До фиксации работ не публиковать реализации в общедоступном GitHub, если нужна строгая слепота. Если доступ общий, явно обозначить это как *процедурную независимость*, не техническую изоляцию.
4. Координатор закрепляет SHA и анонимизирует копии, независимый проверяющий выполняет единые тесты. Пользователь может отдельно оценить понятность кода вслепую. Лишь затем раскрыть авторов и внести результат на [доску](agent-evaluations/LEADERBOARD.md).
5. После сравнения выбрать одну корректную минимальную реализацию (или гибрид после повторных тестов). Никакого автоматического merge; возможен результат «оба не прошли» или «ничья».
6. Никаких R2/R3, второго агента внутри Gemina, визуального 3D движка, истории событий и большой абстрактной инфраструктуры до первого работоспособного ядра.

## Slack / GitHub

- Slack: короткие поручения, подтверждение прочтения, вопросы; не публиковать решения одного конкурента в общем канале до freeze.
- GitHub: контракт, журнал решений, тестовые доказательства, итоговые отчёты, PR. Секретная таблица соответствия Candidate A/B ↔ агенты и сырые материалы до reveal хранится у координатора **в доступном только владельцу месте**, а не в публичном репозитории.
- Публичный рейтинг содержит только завершённые и раскрытые соревнования; предварительные оценки и чужие приватные сведения не публикуются.

**Правило:** сначала работающий объект исследования → затем его свойства → затем расширения. Соревнование — инструмент качества и любопытства, не ещё один этап архитектуры.
