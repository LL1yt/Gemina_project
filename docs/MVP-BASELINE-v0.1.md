# Gemina — MVP Baseline v0.1

**Статус:** APPROVED DIRECTION / implementation NOT_RUN (решение владельца от 2026-11-04).
**Назначение:** единая точка входа для первого воспроизводимого работающего ядра; не новый математический контракт и не разрешение на автоматическое выполнение кода.

> Сначала работающий объект исследования. Затем — исследование его свойств. И только после этого — расширение его возможностей.

## Три уровня работы

**Уровень 1 — рабочее ядро (текущий приоритет).** Один Lion (GRU), стационарное обучаемое тороидальное поле W (16×16×16, 32 параметра на узел как стартовая гипотеза), непрерывная абсолютная адресация, дифференцируемое периодическое трилинейное чтение, R=1 чтение на входной токен, предсказание следующего токена, совместное обучение Lion и W с full BPTT. Во время inference параметры не изменяются. Начальная конкретная конфигурация H=128 / embedding=32 из подробного плана — **proposed engineering defaults**, а не измеренный оптимум.

**Уровень 2 — проверка гипотез (после работающего цикла).** Причинные контроли, равная ёмкость/вычисления, более требовательные задачи, дополнительные варианты инициализации и проверки того, отличается ли обучаемая навигация от хеширования. Не блокировать M1–M4 этим уровнем.

**Уровень 3 — расширения (только после результатов уровней 1–2).** История событий, дополнительные агенты/роли (Eagle, Архивариус), online learning, дополнительные чтения, retrieval, архитектурная кооперация. Отдельные исследования и отдельное разрешение на реализацию.

Для согласования конкретного первого варианта см. [M0 Implementation Passport v0.1](M0-IMPLEMENTATION-PASSPORT-v0.1.md). При оценке coding-агентов используется отдельный [необязательный протокол независимой слепой разработки](proposals/2026-11-04-INDEPENDENT-BLIND-AGENT-EVALUATION.md), а не новый компонент модели; он не меняет приоритет M1–M4.

## Исполнение: узкий маршрут

- **M0:** привести существующие решения и детальный план к единому принятому паспорту; сначала разрешить пересекающиеся документационные решения PR #2 и #5. Прочие открытые Draft PR не сливать автоматически. Реализацию/зависимости/обучение начинать только по отдельному разрешению.
- **M1:** минимальный периодический sampler и детерминированные проверки индексов, интерполяции, wrap.
- **M2:** проверка градиентов координат и W (аналитика, autodiff, finite differences).
- **M3:** один последовательный цикл Lion → address → read W → logits, обратная связь чтения, loss/gradients и короткий observer. **В рамках уже предусмотренной диагностики** измерять до обучения разброс raw u, долю используемых ячеек/узлов и эффективную концентрацию весов чтения; не менять инициализацию до первого воспроизводимого измерения. Не добавлять новый компонент модели ради диагностики.
- **M4:** tiny memorization и один небольшой train/validation запуск; первая цель — подтверждённая техническая обучаемость и воспроизводимые кривые, а не доказательство превосходства.
- **M5:** минимальная генерация, checkpoint / snapshot / replay.
- **M6:** только после M1–M5 — сравнения с GRU-only, frozen W, static/fixed addressing и другими заранее определёнными контролями. Отрицательный или INCONCLUSIVE результат допустим. Дополнительные контроли по R2 и задания R3 из независимого ревью оформляются отдельно и не являются блокером первого работающего ядра.
- **M7+:** прочие эксперименты по отдельному разрешению.

Источник конкретных математических, интерфейсных и тестовых контрактов — [Draft PR #5](https://github.com/LL1yt/Gemina_project/pull/5). Выбранное направление свободной абсолютной адресации — [Draft PR #2](https://github.com/LL1yt/Gemina_project/pull/2); независимая рецензия и альтернативы — [Draft PR #8](https://github.com/LL1yt/Gemina_project/pull/8). Ветки пока не объединены с main и не становятся автоматически утверждёнными спецификациями от одной ссылки.

## Граница изменений по результатам независимого ревью

| Пункт | Решение для MVP v0.1 |
|---|---|
| R1: адреса сходятся в одну ячейку при старте | **Минимальная диагностика M3** как наблюдение; исходную инициализацию не заменять без результатов. Если адресация/градиент математически неверны — это блокер M1–M3. |
| R2: Frozen Random Head и Token-only | **Уровень 2**, уточнить контроль с учётом обучаемой GRU. Не блокировать M1–M4. |
| R3: ёмкостная задача и compute-matched | **Уровень 2**, после первого learning sanity; заранее регистрировать условия сравнений. |
| R4: learning rate W | Зафиксировать исходную сетку в M0/M4, записывать фактические обновления; равный LR допускается как отдельная заранее объявленная настройка, не тихая замена default. |
| R5: периодический шов и FP32 | Проверять численную корректность в M1–M2 и отмечать большие raw u; не строить дополнительных абстракций. |

## Правила изменения baseline

1. Сначала **минимально необходимая реализация и проверки**, без универсального framework, UI-платформы и системы нескольких агентов.
2. Критический математический дефект, пропавший градиент, потеря параметров, неверная последовательность или нарушение данных — основание остановить соответствующий этап и исправить.
3. Дополнительный контроль или повышение качества эксперимента, не влияющий на корректность ядра, фиксируется в backlog/отдельном Draft PR, но **не задерживает** M1–M4.
4. Каждый PASS требует реально выполненной проверки, seed/окружения и артефакта; всё до запуска — NOT_RUN. Ни одна рецензия другого ИИ не заменяет тестов.
5. Никто из агентов не меняет main, чужие ветки или этот baseline без прямого поручения владельца. Разговоры Slack — координация; GitHub — источник истины по состоянию проекта.

**Следующее реальное действие:** рассмотреть и закрепить подготовленный M0-паспорт, отдельно проверить совместимость toolchain и только затем отдельным поручением открыть реализацию M1–M4. Не начинать с исследований R2/R3 и не создавать новый слой архитектуры ради ревью.
