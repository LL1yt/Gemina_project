# Gemina — независимые тесты sampler и сотрудничество coding-агентов

**Дата:** 2026-11-02. **Статус:** DRAFT / PROPOSED AGENT WORKFLOW.  
**Текущая граница:** документационное поручение; тесты, код, CI, сборки и обучение **NOT_RUN**. Запись этого плана не даёт полномочия начать M1/M2 или подключать новый GitHub App.

## 1. Когда выдавать задание

- **Сейчас (проектирование, до разрешения реализации):** сохранить единый математический контракт и два независимых задания. Можно отдельно поручить Claude прочитать PR #5 и дать review *без изменения файлов*; это не исполнившаяся проверка sampler.
- **После отдельного разрешения на реализацию, на выходе M0 / перед реализацией sampler в M1:** зафиксировать точный [Mathematical / Interface Contracts](MATHEMATICAL-INTERFACE-CONTRACTS.md), ревизию/хеш и допуски [Test Matrix](TEST-MATRIX-ACCEPTANCE.md). Выдать **одно и то же задание** двум независимым coding-агентам. Каждый должен составить собственные fixtures, expected values и план тестов **до знакомства с тестами и кодом другого агента**.
- **M1 (sampler values):** после независимого согласования артефактов интегрировать тесты в отдельные ветки/PR и сравнить их с реализацией, только после отдельного разрешения на код. Проверять S01–S05.
- **M2 (gradients):** реализовать/исполнить независимые G01–G04, проверить аналитический gradient, autodiff и конечные разности. Только после успешного M1.
- **M3+ / M6:** затем тестировать полный цикл и обучаемость; сравнения GRU относятся к **M6**, не к M1/M2.

Если независимые задания выдаются в рамках текущего документационного этапа, результат ограничить review/текстом или Draft PR с *только документацией*: ни тестовый код, ни dependency resolve, ни inference не разрешены.

## 2. Общее задание двум независимым агентам (дословно одинаковый текст)

> Ты — независимый проверяющий математического sampler Gemina.
>
> Репозиторий: https://github.com/LL1yt/Gemina_project. Прочитай AGENTS.md и docs/START-HERE.md, затем **один общий для двух исполнителей** исходный контракт docs/plans/2026-11-02-mvp/MATHEMATICAL-INTERFACE-CONTRACTS.md и матрицу TEST-MATRIX-ACCEPTANCE.md на заранее названном commit SHA. При изменении SHA остановись и сообщи о расхождении.
>
> Независимо от второго исполнителя выведи проверочные примеры, аналитические ожидаемые результаты и тестовый план для **периодического 3D trilinear sampler**: corner ordering/flatten indices; λ и сумма весов; отрицательные/очень большие координаты и период 16; швы 0/16; отдельные каналы; batch independence; повторные узлы при выборке и суммирование градиентов; градиенты по W и непрерывной raw-координате; finite differences строго внутри ячеек; одностороннее поведение на гранях.
>
> Тесты должны включать hand-computable fixtures (не только сравнение функции с самой собой), непостоянное W для проверки coordinate gradient и контрольные невыбранные узлы с нулевым локальным ∂read/∂W. Отдели проверки математического контракта от проверок конкретных MLX API. Не считать центральную конечную разность на изломе эталонной производной.
>
> Для каждого теста укажи ID, исходные W/координаты/seed, аналитический ожидаемый результат, тип сравнения (точно / абсолютный+относительный допуск), причину возможного FAIL, какие ошибки он ловит, и ограничения на применение. Не изменяй формулы или допуски, чтобы тест начал проходить.
>
> **Сначала подготовь независимый дизайн и fixtures без просмотра реализации sampler и материалов второго исполнителя.** Открой свою отдельную рабочую ветку и Draft PR только при наличии явного разрешения на запись; не изменяй main/PR другого агента. Исполняемый тестовый код, установка зависимостей, сборка или запуск — **только после отдельного разрешения на этапы M1/M2**.
>
> Никогда не выполняй merge, auto-merge, изменение protection/ruleset, управление репозиторными разрешениями или удаление чужой ветки без отдельного прямого поручения владельца. Не выдавай инструкцию в AGENTS.md за техническое ограничение собственных прав.
>
> Верни список fixtures и потенциальных несоответствий спецификации; отмечай NOT_RUN всё, что фактически не проверялось.

**Изоляция:** одним из исполнителей может быть Codex/OpenAI, другим Claude Code. Каждый видит одну версию исходных контрактов, но **не** черновик второго до фиксации своего результата. Следует не выдавать первому агенту реализацию второго или его тесты как «общий контракт». Разработчик sampler может быть третьим участником; если его код уже создан, до публикации независимых expected values не показывать его тестовым агентам.

## 3. Как сопоставить независимые результаты

1. Сохранить SHA контракта и два независимых Draft PR/документа; зафиксировать, какой агент что читал, и какие проверки фактически исполнялись.
2. Сопоставить ID, fixtures и expected values, не подгоняя один набор под другой. Выделить совпадения, расхождения и недостающие пограничные случаи.
3. Расхождения разбирать от математических формул и независимых простых примеров, не по «большинству моделей». Если оба агента скопировали ошибку контракта, независимое согласие ничего не доказывает.
4. После разрешения исполнения прогнать на одной реализации оба набора тестов и отдельный ручной/скалярный reference. Проверить фрагменты графа градиента и произвольную случайную fixture с сохранённым seed.
5. Если тест нарушает контракт, остановить M1/M2 и сохранить failing fixture; **не** исправлять тест ради совпадения с текущей реализацией. Изменение контракта — отдельное явное решение и повторное выполнение независимых проверок.
6. Завершение этой схемы **не равно** проверенной семантике W, успешному обучению Lion или превосходству над GRU.

## 4. Минимальные права Claude и других сторонних агентов

- GitHub App при подключении: выбрать **Only select repositories → Gemina_project**, если интерфейс установки предоставляет выбор; просмотреть запрошенные Content, Pull requests, Issues, Workflows и другие права. Начать с чтения для независимого review; запись предоставлять лишь для конкретной задачи с отдельными PR. Не давать доступ ко всему Project_Index/другим приватным репозиториям автоматически.
- Инструкции в AGENTS.md и в задании задают **ожидаемое поведение**, но не ограничивают технические возможности токена/GitHub App. Если интеграции предоставлена write/merge-capable роль, само предложение «не сливать» технически не блокирует merge.
- Для реальной защиты main при поддерживаемом GitHub плане включить в **Settings → Rules → Rulesets** или **Branches**: require pull request; require review/status checks по мере появления CI; запретить force-push/deletion, ограничить bypass. GitHub Pro/Team/Enterprise поддерживают такую защиту и для private repos; в других планах доступность проверять в UI. **Этим документом правила GitHub не меняются.**
- Не включать auto-merge и не разрешать агентам push в main. По возможности разделить «чтение для review» и «отдельная ветка/PR для реализации». После завершения работы можно отозвать доступ через GitHub Settings → Applications → Installed GitHub Apps.
- Сохранять приватность кода: до подключения стороннего сервиса изучить его конкретные условия использования данных и доступные настройки. При необходимости проводить независимое ревью только переданных фрагментов контрактов.

## 5. Связь с первым сравнением GRU

Эта пара независимых sampler-тестов **предшествует** сравнительным экспериментам M6. Даже идеальное совпадение S/G-проверок — только доказательство корректности чтения и производных, не пользы поля. Первый сравнительный контроль M6-A — **Gemina Lion H=128 vs GRU-only H=128** на одинаковых held-out данных и бюджете. Далее контроль обучаемости W и адреса; затем M6-B — **GRU-only H=248 с близким суммарным числом параметров**. Строгие интерпретации и ограничения — [Training and Evaluation Protocol](TRAINING-EVALUATION-PROTOCOL.md) и [Test Matrix](TEST-MATRIX-ACCEPTANCE.md).
